# DECISIONS (estratto-engine 1.0.0-rc.5)

Decisions made while building the first version without asking questions. Anything that deviates from arm-public.mjs is listed here.

## 1. Changes to core/ (the only three files that differ from P80)

Every other file under `core/` is byte-identical to `/home/claude/p80` (checked by `test/09-core-integrity.test.js` against `core/CORE-MANIFEST.json`).

1. `core/main/ask.js` line 81 (`irCatalogOn`)
   - P80:  `return (o && o.irCatalog === 'system') || process.env.STUDIO_IR_CATALOG === 'system';`
   - here: `return !!(o && o.irCatalog === 'system');`
   - Why: the engine core must never read `process.env`. With the variable unset (the benchmark situation) both versions return the same value; the engine never passes `irCatalog`, so behaviour is identical. Without the change a host that happened to export `STUDIO_IR_CATALOG=system` would silently change the prompts.
2. `core/worker/embed.js` lines 77-78 (`e5Dir`)
   - P80 had two fallbacks after the explicit `dir` argument: `process.env.STUDIO_E5_DIR` and `process.env.STUDIO_MODELS_DIR`. Both lines removed.
   - Why: same rule. The engine always passes the model directory explicitly, so those lines were never reached; behaviour identical.

3. `core/main/auto-semantics.js` line 56 (`normCur`) -- rc.2, red-team a4
   - P80: `return /^[A-Za-z]{3}$/.test(s) ? s.toUpperCase() : null;`
   - here: adds `const ISO_4217 = new Set('AED AFN ... ZWL RMB'.split(' '))` (ISO 4217 active codes + RMB) and returns the upper-cased code only if it is in that set.
   - Why: in auto-rules mode any 3-letter cell value of a currency column became a "currency code" and was written into the SQL-fallback system prompt (a data value leaving the machine). Only the auto-rules path calls `normCur` (via `buildAutoPack`); benchmark runs use rule packs and never reach it, so their requests are unchanged.

Not copied (not in the ask.js closure): `ask-service.js` (reads 27 files at load for CODE_VERSION), `workers.js`, `main.js` and everything Electron (`main.js`, `preload.js`, `secrets.js`, `dsh-skin*.js`). `auto-semantics-app.js` and `patch-service.js` are copied but their lazy requires of `ask-service`/`workers` are never executed (`makeHubNamer` and `measureUniqueness` are not used).

## 2. Wiring: what is identical to arm-public.mjs, what differs

Identical: `SemanticRegistry.load({packs, tables: meta, partial: true})`; `EntityLookup` filled from DuckDB distinct values (column dims, date-like skipped by the same regex, > 2000 distinct skipped, 5000 value cap); `planExecutor.execute(plan, {registry, cards})` with a `cards.worker.call('semanticQuery')` adapter; the table-metadata type heuristic (`INT|REAL|NUM|DEC|DOUBLE|FLOAT|HUGEINT|UBIGINT|BIGINT` -> number, name matches `date|month` -> date, else text, including its quirks); `ask()` option set (maxCallsPerQuestion 2, maxTokensPerQuestion 2000, maxCallsTotal 4, sqlLane on, sqlRunner = connection `run`, anchor, timezone Asia/Shanghai, `scope {workspace}`, dataStamp, permissionVersion, codeVersion, provider/model, callLog, `allowLocalZeroCall:false`); `resolveIR` = `buildIRMessages(payload + question)` -> chat call -> `parseJsonLoose` -> callLog entry before parsing, same entry fields; body of the OpenAI-compatible call (test 01); the `model_reasoning_only` rule; ANSWER-line extraction; raw.json fields; `ReuseCache` with `SqliteReuseStore`; `FactBook`; e5 vectors (`unit-vector dot product`, text cache, silent-to-warning fallback).

Differences (all deliberate):
- **One connection per ask()** (`db.session()`), not one per process. Needed for cancellation (`connection.interrupt()`) and so concurrent questions cannot interfere through connection settings (`SET enable_external_access`, `disabled_optimizers`).
- **Fresh `FactBook` and `ReuseCache` object per ask()**, over one shared `SqliteReuseStore` per engine (`dataDir/reuse.db`, namespace `estratto`). arm-public runs one question per process, i.e. also a fresh FactBook/ReuseCache per question; sharing one FactBook across questions would grow fact ids F1..Fn forever and leak facts between questions.
- ask() additionally receives: `signal` (cancel), `cancelSql` (interrupt the running SQL on timeout/cancel), `rememberValue`/`lookupValueAlias` (persist a user-confirmed value reading in `dataDir/value-aliases.json`; only used after `engine.confirm`), `audit` (collected into events instead of `audit.jsonl`). arm-public passes none of these; none changes the result of a first-time question.
- `thinkingRepair` defaults to `thinking` (arm-public defaulted both to `false_bool` independently; with defaults the result is the same).
- The `x-opencode-session` header is not sent (benchmark-proxy specific). Extra headers can be passed with `openaiCompatible({headers})`.
- `maxOutputTokens` is used for first call and repair (arm-public's code uses MAX_OUT for both although its comment says 900 for repairs).
- `dataStamp` is computed (file name + hash of size, mtime, row counts, columns), arm-public hard-coded one. `codeVersion` = `estratto-engine@<package version>`; it is part of the reuse key, so a new engine version invalidates old cache entries.
- Each engine loads a **private copy of `core/worker/embed.js`** (cache-busted `require`), because that module keeps loaded ONNX sessions in a module-level table keyed by model id; sharing it would let two engines with different `modelsDir` see each other's model.

## 3. Privacy transport (src/privacy.js)

Port of `assets/guard/studio-privacy.cjs` `protect()` with `assert` replaced by "refuse". Applied to every request inside `resolveIR` (IR lane and SQL lane); the host's `generate()` only ever sees the protected messages and cannot switch the transport off. Beyond the original guard:
- `candidates` must be the compact tuple shape (`metrics|dimensions|time_roles`, items scalars or arrays of scalars); anything else is refused.
- `system`/`user` message content must be strings; `entities`/`previous_errors` must be arrays when present.
- On refusal: event `outbound_blocked {requestId, reason}`, `status:'refused'`, `refusal.code:'outbound_blocked'`, the request is aborted (no further attempts), the model is never called, and nothing is cached.

Not covered by the guard (same as the benchmark): the **system** message is not inspected. It is built by core from table structure and registered rules (metric/dimension names, algorithms, units, currency codes, date formats, relation lists). In auto-rules mode the counts measured on data that auto-semantics embeds in `return_notes` ("有 N 行负数") are scrubbed to "若干行" by the engine (test 02). `catValues` (category value lists) is never populated in this wiring, so no value lists are sent. If rules supplied by the host contain data values in aliases/notes, those go out too: rules are trusted input.
- `_testMutateOutbound` (undocumented option) lets tests corrupt the outbound messages *before* the transport to prove the refusal path. It cannot bypass `protect()`.

## 4. Rules (no `rules` given)

`buildAutoPack` (main/auto-semantics.js) is called directly with DuckDB-typed columns and no model namer (dictionary + rule naming only; Chinese names for English columns come from the dictionary). The pack is persisted to `dataDir/rules/auto-pack.json`; a re-run keeps entries that were confirmed (`previous`). Auto metrics/dimensions are marked `auto:true, confirmed:false`, so answers that rely on them are `needs_confirm`; `engine.confirm(id, 'accept')` flips exactly the auto items the answer used to `confirmed:true` (decided_by `host`) and re-answers (0 model calls, verified). I did not use `auto-semantics-app.refreshAutoSemantics`: it only handles views named `v_t<hex>` produced by the desktop app's import and needs a worker object.
Imported table names are the sanitized file name (`sales.csv` -> `sales`; xlsx sheets: `<book>_<sheet>` when a workbook has several sheets).
When `rules` is given, only those packs are loaded (like arm-public's single pack), not the six built-in domain packs in `core/main/semantic/` (they are kept because `dict/contracts.js` requires them and `PatchService` loads them).

## 5. Rules patches (engine.rules)

`engine.rules` wraps `PatchService`/`PatchStore` under `dataDir/rules` (`patches.json`, `generated/*.json`). `confirm/reject/revert/propose` are async because the registry and entity lookup are rebuilt afterwards (confirmed patches become `generated/` packs loaded on top of the host's packs). The decider defaults to `by:'host'`; the store still refuses `by:'model'`. `list()` reads the store directly and does not use `PatchService.snapshot()` (that loads the built-in packs). External edits to `patches.json` are picked up at the next `ask()` (`ensureFresh`). Relation verification (`verifyRelation`) is not exposed: it needs a worker for uniqueness measurement.

## 6. Status mapping (src/status.js, test 05)

Verified in core source: `ok` -> verified; `ok` + `result_status:'no_data'` (config lane, and sql lane ask.js:2257) -> no_data; `ok` + `value_guess(es)` / `tier:'pending'` / auto names (`tier_why.auto_names`, fact `tier:'pending'`) -> needs_confirm; `tier:'unverified'` -> unverified; `needs_clarification` (all codes, incl. `value_choice`, `missing_time_role`, `plan_incomplete`, `role_mapping_unconfirmed`) -> needs_confirm; `capability_gap` -> refused; `error` -> error; cancel -> cancelled. Note: `needs_clarification` with code `missing_required_input` (core "data does not contain X") also maps to needs_confirm, following the spec literally. `raw.status` keeps the core status (`ok`, `capability_gap`, ...); the engine status is `r.status` and `raw.engine.status`.
`route`: `sql` when lane is sql, `reuse` when the result cache served it, `local` when no model call was made, else `plan`.
`meta.checks` are derived from the core trace (`validate_ir`, `sql_check`, facts present, `self_check` layer) plus `privacy_outbound`; they are not model self-assessment.

## 7. engine.confirm(requestId, choice)

- `value_choice`: `choice` = option index, option value, or `{value}`; must be one of the offered options; SQL lane uses `valueChoice.sql` (0 model calls), config lane re-asks with `valueChoice` (entity pick). The picked value is stored in `value-aliases.json` and removed from the "guess" list, so the answer is `verified`.
- value_guess / pending plan: `choice:'accept'`; auto names are flipped (see 4); re-ask with `confirmedPlan`.
- Other clarifications (metric, time role, dimension): `choice` = option index/id; the question is re-asked with the option's name appended in brackets. This is a pragmatic first version, not the desktop app's UI flow.
- Pending confirmations are kept in memory (last 200); they do not survive a restart.
- Pending `tier:'pending'` caused by "new algorithm" (not auto names) cannot be turned into `verified` in v1: `accept` re-answers and the status stays needs_confirm.

## 8. Other

- Node >= 22.5 (`node:sqlite`; Node prints an ExperimentalWarning). Tested on Node v22.23.4, linux-x64. DuckDB: `@duckdb/node-api` 1.5.5-r.5 (exactly p80's requirement; installs fine on linux-x64).
- `package.json` `exports` maps `import` to `index.mjs`, `require` to `index.js`.
- `files`/xlsx import: exceljs reads the whole workbook in memory, then each sheet goes through a temp CSV and `read_csv_auto` (type inference by DuckDB). Dates become ISO strings. Re-opening an engine with unchanged files (path, size, mtime) skips the import.
- CLI exit codes: 0 verified, 3 needs_confirm/unverified/no_data, 1 other, 2 usage.
- Not claimed anywhere: benchmark numbers. Parity is shown only at the level of request body, wiring and core bytes.


## 9. rc.2 changes (red-team fixes). All in src/ except core item 1.3 above; normal (benchmark) request bodies are unchanged.

1. Secrets: `openaiCompatible` redacts the api key, `Bearer ...`, `sk-...`, `oc_sk_...` from provider error text/messages and exposes only a `redact()` function (never the key). The engine passes every result, raw, event and `writeAttempt` file through `src/redact.js` (literal key from the adapter + token patterns); the CLI redacts everything it prints (and `ESTRATTO_API_KEY`).
2. ANSWER spoofing: after `parseJsonLoose`, every string in the model's IR (keys too) has C0/C1 controls, CR/LF, U+2028/2029 replaced by a space (`scrubControl`). `answer` keeps only its first line starting with `ANSWER`; later such lines are demoted (`- ANSWER...`). Side effect: newlines inside a model-written `sql` become spaces, so a `--` line comment in model SQL would comment out the rest.
3. SQL catalog: `sqlRunner` wrapper rejects model-written SQL (the `SELECT * FROM (...) AS _sql_lane LIMIT n` execution wrapper and the `json_serialize_sql(...)` parse step) containing the identifiers `duckdb_*`, `information_schema`, `pg_*`, `sqlite_*`, `pragma_*` (bare or quoted, any case; string literals with those words are also rejected). Core's own metadata queries (`information_schema.columns` for column types) are not model SQL and still run. Rejection throws into the core's normal SQL failure path. DuckDB instance gets `memory_limit` = `limits.memoryLimit` (default `'2GB'`); core still sets `enable_external_access=false` on the first model SQL.
4. Currency whitelist: see core item 3.
5. Transport: `_testMutateOutbound` removed (tests wrap `buildIRMessages` in a private module copy). `protect()` additionally refuses: entities items with keys other than `dim`,`value` or non-string dim/value (previously non-string values were silently dropped); `period` not a plain object of short strings/numbers (null values allowed); `anchor`/`timezone` not short (<=64) strings (null allowed); candidate tuples with non-strings (null allowed); `tools`/`functions`/`tool_choice`/`function_call` present. Refusal only; accepted requests are not modified except the existing entity filtering.
6. Caps: IR with >200 entities, >2000 array items (deep), or a response text >1,000,000 chars is refused before core processing (`model_error` -> status `error`, message "IR refused (resource cap)"). `usage` larger than 16 KB is cut to the standard numeric token fields (plus `reasoning_tokens`/`cached_tokens` in the `*_details`).
7. Permissions: dataDir and subdirs 0700; `reuse.db`, `-wal`, `-shm` created 0600 before SQLite opens them; rules tree, `value-aliases.json`, `import.json`, auto pack, imported `warehouse.duckdb` (+wal), temp xlsx CSVs and `writeAttempt` outputs 0600. A user-supplied DuckDB file is not touched. Existing dataDir directories are not re-chmod-ed except the engine's own subdirectories (a pre-existing dataDir keeps its mode).
8. xlsx: if a first-row cell is longer than 64 chars or fewer than half of the cells are filled, event `import_warning` is emitted, columns are `col_1..col_n`, and that row is kept as data. CSV unchanged.

### Known limitations carried into rc.2 (documented, not fixed)
- Repair side channel (red-team a7): whether a repair request follows a failed local query depends on the data. A malicious model provider, or a prompt injection that controls the model, can infer a few bits per question about the data from that. Fixing it changes answering behaviour; planned for 1.1.
- The system message is not inspected by the transport; it is built only from table structure and rules (rules are trusted input).
- Auto-rules date-format detection uses samples of cell values locally; only the detected format (not the samples) appears in prompts.

## rc.2 follow-up (Claude review)
- The IR control-character scrub no longer touches CR/LF/TAB inside fields named `sql`: replacing the line break after a `-- comment` with a space would comment out the rest of the model's query and make the SQL lane behave differently from P80. ANSWER spoofing through SQL text is still prevented by the first-ANSWER-line rule.

## rc.4 changes. All in src/ (no core/ file touched; core/CORE-MANIFEST.json unchanged). Request bodies of normal questions with a supplied rules pack are unchanged.

1. Auto confirmations are records (`dataDir/rules/auto-confirms.json`, `{id:'ac_…', kind:'auto_confirm', status:'confirmed'|'reverted', items:[{kind,id}], refs, decided_by:'host', at}`). `engine.confirm(id,'accept')` on auto-named items writes one (only when something was actually flipped in `auto-pack.json`). `engine.rules.list()` returns patches plus these records (filters `status`, `origin`, `kind:'auto_confirm'`); `snapshot()` adds `auto_confirms`. `engine.rules.revert(x)` accepts a record id or a metric/dimension id (`m:`/`d:` prefix optional; `items` match first, then `refs` = plan.metric_ids/dims of the confirmed answer; the newest live record wins), sets the items back to `auto:true, confirmed:false`, rewrites `auto-pack.json`, rebuilds registry + entity lookup, clears reuse.db plan/result/kv caches (blunt: nothing that depended on the reading survives). Unknown ids still fall through to `PatchService.revert` ("no such patch"). A reverted record cannot be reverted twice. Everything is on disk, so it survives restart.
2. Unsafe identifiers (src/hostile.js): a table or column name with C0/C1 controls, CR/LF, U+2028/2029, or longer than 64 characters is removed from the metadata used for registry, entity lookup, auto rules, SQL context, privacy schema and the data stamp. Event `import_warning {table, column (first 16 chars + '…', controls shown as spaces), reason: control_characters|longer_than_64, action:'excluded'}`. `engine.tables()` lists them redacted with `excluded:true`. Without such names metadata objects are passed through untouched.
3. File imports: such columns are renamed `col_<position>` (next free number on collision) right after the table is created, warning `action:'renamed', renamedTo`; warnings are stored in `import.json` and repeated when an unchanged warehouse is reused. A file name that sanitizes to more than 64 characters is shortened (60 chars + `_<k>` if needed) with a warning.
4. `duck.js` `describe()` quoted table names with `JSON.stringify` (wrong for names with line breaks or quotes); now uses the same `"` quoting as every other query. Identical for ordinary names.
5. README quickstart: the pack and a matching CSV ship under `examples/` (added to `files`); no reference to `test/fixtures`.

## rc.5 changes (src/ only)
- `rules.confirm(id)` / `rules.reject(id)` accept `auto_confirm` record ids. confirm on a reverted record re-confirms the SAME record (status `confirmed`, `reconfirmed_at/by` set, items flipped back in `auto-pack.json`, registry/lookup rebuilt, reuse caches cleared; survives restart); on an active record it throws "already confirmed". reject on an active record behaves like revert; on a reverted record it throws "already reverted". revert/confirm/reject share one code path. Other ids still go to PatchService.

## 1.0 workspace & surfaces (rc.6). src/, bin/, docs/, tests only; core/ untouched (CORE-MANIFEST.json unchanged)

Compatibility rule: with no `privacy.hiddenColumns`, no ledger/budget and no refresh configured, `createEngine` runs the rc.5 code path. Replay check: 6 questions (plan lane, local, reuse, SQL lane, repair) against rc.5 and rc.6 with a supplied pack produced 19 model requests, byte-identical (also with `privacy:{hiddenColumns:[]}` and `limits:{}`).

1. **Workspace** (`src/workspace.js`). `<home>/<name>/` is the engine's `dataDir` itself (warehouse, rules/, reuse.db, import.json) plus `estratto.json`, `secrets.json`, `usage.jsonl`. Directory 0700, files 0600, config written atomically (temp + rename). The library never reads `process.env` or `os.homedir()` (the static guard test forbids it): `home` is mandatory in the library and the CLI passes `ESTRATTO_HOME` / `--home` / `~/.estratto`. `openWorkspace` returns more than the contract lists: `use(fn)`, `ask`, `confirm`, `cancel`, `addSource`, `keyStatus`, `redact`, `on(listener)`, `expandSources`; `engine` is a getter because some settings rebuild the engine.
2. **Config schema**: validated by hand (no dependency), unknown keys are errors naming the path. `model.thinking` accepts `none` (send no thinking field; default for `openai`/`custom`, `disabled` for `deepseek`). `data.refresh` is `auto|manual`. Extra field `surfaces.serve.allowedOrigins`. A DuckDB source excludes every other source (message "A workspace uses either ONE DuckDB file or any number of files/folders..."). A folder source takes a `*`/`?` glob (default `*`) and only csv/tsv/xlsx/parquet (`.txt` only when the pattern asks for it); dot files and `~$` files are skipped; the folder is re-read at every refresh.
3. **What rebuilds the engine**: changing `rules.packs`, `privacy`, `behavior`, `limits.max*`, `model.provider/model`, `data.refresh` or the DuckDB source. What applies live: key, `baseURL`, `thinking`, price, `dailyBudgetUSD` (the model is a wrapper that reads them per call; the ledger is shared), and adding/removing file/folder sources (an incremental refresh, no rebuild). A rebuild waits for running asks (up to 60 s) and rolls the config back if the new engine cannot start.
4. **Key handling**: the key exists in `secrets.json` and in the model wrapper's closure. Everything the workspace hands out (events through the engine redactor, `ws.redact` for HTTP / MCP / CLI) goes through `makeRedactor` with every key the process has seen. HTTP never echoes request bodies in errors (a malformed JSON body is "not valid JSON", not the parser message). Tests grep every file of the workspace for the key and expect `secrets.json` only.
5. **Hidden columns** (`createEngine({privacy:{hiddenColumns:['table.col']}})`, case-insensitive). Applied right after the rc.4 hostile-name screen to the metadata the registry, entity lookup, auto rules, SQL context, privacy schema and data stamp are built from. Additionally, rules of a *supplied* pack that are built on a hidden column are dropped (simple metrics on it, ratio/derived metrics that use those, dimensions whose `role`/`source` is it, relationships using it): otherwise the metric definition ("销量 = SUM(sales.qty)") would still name the column in the SQL-lane prompt. A table whose every column is hidden is not described at all. `tables()` lists hidden columns with real names and `hidden:true` (the owner needs them to un-hide); `info().hiddenColumns` lists them. Model-written SQL that contains a hidden column's name as an identifier (bare or quoted, any case, any table) is rejected locally (`sql_hidden_column_blocked`); this is name based, so a hidden column called `id` blocks SQL that uses `id` of another table too. Unknown entries give a `warning` event once.
6. **Data auto-refresh** (`data.refresh:'auto'` in `createEngine`; the workspace passes it from `data.refresh`). Before an ask, at most every `data.refreshIntervalMs` (default 5000; the clock starts at engine creation): files by `size:mtimeMs`, new/removed files too when `data.resolveFiles` is given (workspace folders); DuckDB by file `size:mtimeMs`. It waits for running asks to finish (up to 30 s, otherwise tries again at the next ask), then closes the connection and re-imports **only the tables of the changed file**, each file in one DuckDB transaction (`importFiles(..., {update:{changed,removed}})`): a file that cannot be read keeps its old tables, emits a `warning` event `data_refresh_failed`, and is not retried until its size/mtime changes again. The import manifest keeps the old stamp of files that were not re-imported, so a restart still re-imports a failed file. DuckDB source: the new connection is opened first, then the old one is closed. Rules are kept; with auto rules the pack is regenerated (previous confirmations and "not right" marks kept) only when the column set changed; the registry and entity lookup are rebuilt. `dataStamp` changes (it includes size, mtime, row counts), so cached answers of the old data are never served. Event `data_refreshed {files, tables, dataStamp}`. `engine.refreshData()` forces a check; `info().lastRefreshAt` / `dataUpdatedAt`.
7. **Daily budget** (`src/ledger.js`). `createEngine({limits:{dailyBudgetUSD, price:{inputPerM,cachedInputPerM,outputPerM}}, usageFile?, ledger?})`; with none of them there is no ledger at all. One `usage.jsonl` line per model call (`{at, day, requestId, providerRequestId, model, usage, costUSD}`; `day` is the date in `behavior.timezone` when it was recorded). Cost = uncached input x inputPerM + cached input x cachedInputPerM + output x outputPerM; cached tokens from `prompt_tokens_details.cached_tokens`, `prompt_cache_hit_tokens` or `cache_read_tokens` (uncached from `prompt_cache_miss_tokens` when present, else prompt minus cached). Without a price the cost is 0 but the line is still written. The check happens **where a model call would be made**, not at the top of `ask`: that is the only way to keep "cache hits and local plans still answer when over budget". Over the limit (spent >= limit, so `0` blocks everything) the call is not made, the ask resolves `status:'refused'`, `refusal:{code:'daily_budget_exceeded', spentUSD, limitUSD, day}` and a plain `answerLine` in the workspace language; event `budget_exceeded`. The model call that crosses the limit is not interrupted, so the day can end slightly over the limit.
8. **Rules** (`engine.rules`). New: `metrics()` (state per metric: `unconfirmed|confirmed|reverted|rejected|provided`; `provided` = from a supplied pack, `auto_confirm` records only exist for auto rules), `preview(id)`. `confirm(metricId)` on an auto metric/dimension creates the same kind of `auto_confirm` record an answer-time confirmation would (just that one item; dimensions it is used with stay unconfirmed until confirmed), or re-confirms its reverted record. `reject(metricId)` on an unconfirmed auto item marks it `rejected:true` in `auto-pack.json`: it is left out of the registry until `revert(metricId)` (the contract's "改为不对"); on a confirmed item it is a revert. Rejection marks survive the auto pack regeneration at start-up. `preview` builds a `plan-ir/2` plan and runs it through `plan-executor.execute` (the executor all answers use): total = no period, last month = `grain:'month'` rows, the latest label before the month of the anchor (so "last complete month" means the last month before the anchor month that has data). Id may be a metric id, an `auto_confirm` record id or the `requestId` of a pending answer. No model call.
9. **HTTP** (`src/serve/index.js`, `docs/HTTP-API.md`). Order of checks: Host, Origin, token, role. `/settings` additionally needs the owner key in the URL (printed by `estratto serve`); without it anyone who can open `/` could read the owner key from the page. `accept` on `/api/confirm` is owner-only because accepting a plan flips auto rules to confirmed. Only `data.refresh`, `model.*`, `limits.*`, `privacy.hiddenColumns`, `behavior.*` are editable over HTTP; sources go through `/api/data/add`; packs, `access`, `surfaces` (incl. `allowedOrigins`, `allowRuleChanges`) are CLI/file only. Bodies: JSON only, 64 KB. A closed connection cancels the running ask. Responses carry `Cache-Control: no-store`, `nosniff`; pages carry a CSP. Static files: single-segment names, extension whitelist, `realpath` must be directly inside `ui/` (no listing, no nesting, no symlink escape). The session token is compared in constant time.
10. **MCP** (`src/mcp.js`) uses the SDK's low-level `Server` with plain JSON-schema tool definitions (no zod dependency of our own). Tools `ask`, `list_tables`, `list_rules`; `confirm_rule`, `revert_rule`, `confirm_choice` are neither listed nor callable unless `surfaces.mcp.allowRuleChanges` is true. Results: text (answer, `status:`, confirmation options with the requestId) plus `structuredContent` `{requestId,status,answer,answerLine,route,confirm,refusal}`; no rows, SQL, plan or raw. Rule changes made over MCP are recorded with `decided_by:'mcp'`. In `estratto mcp` all CLI output goes to stderr (stdout is the protocol).
11. **CLI**. `init --yes` never prompts; without `--yes` it needs a terminal (otherwise exit 2). Interactive mode uses `node:readline`; the key prompt uses a muted output stream (verified in a pseudo-terminal run: the typed key is not echoed). Non-interactive key: `ESTRATTO_API_KEY` (also for `config set-key`). `init` never edits another program's configuration: it prints the MCP snippet (`command` = the absolute node binary, `args` = this `estratto.js mcp --name ... [--home ...]`) and the serve command. `rules export` writes a 0600 JSON (`estratto-rules-export/1`: metrics with state, records, patches); `rules import` re-applies confirmations and "not right" marks of auto metrics by id (patches in the file are not imported). `config get` hides `access.ownerToken`; `config set` refuses `access.*`, `name`, `version`, `data.sources`. `doctor` checks Node, permissions (loose permission on estratto.json/secrets.json is a failure), config, sources, model fields, key, vector model, usage log, opens the engine; `--online` does `GET <baseURL>/models` (the key goes only to the configured server). ## rc.7 changes (src/, bin/, ui/, docs/, tests only; core/ untouched, CORE-MANIFEST.json unchanged)

Parity rule: every behaviour change that can touch an ask() is gated on **auto-rules mode** (`createEngine` without `rules`). With a supplied pack the request path, the request bodies and the answers are the rc.6 ones. Checked by replaying 4 questions (plan lane, local, share/average wording) against the rc.6 build with a supplied pack: request messages, status, route, answer and confirm card are byte-identical (`test/16-rc7.test.js` keeps the rate-worded cases as a regression test). Things that are not gated because they cannot fire in pack mode: the `d:`-aware revert lookup, `engine.rules.dimensions()` (new API), the CLI/HTTP/MCP additions, the dimension preview.

1. **Rate / share / average wording** (`src/rate-guard.js`, called in `run()` after the core answered, auto mode only, every route). Question side: 率, 比例, 占比, 比重, 百分比, 平均, 均, rate, ratio, share, percent(age), average, avg, a lone `%` (not "10%" inside a filter), and `per <order|customer|user|unit|item|click|session|visit|day|transaction|piece|ticket|sku|product|employee|head|capita>`. Plain `per` ("sales per channel") is a grouping and is deliberately NOT a rate word. The core's `askedConcepts` / `unsupportedConcepts` were not used: they extract concept nouns for refusals and do not know the answer's kind. Answer side (typed result, never numbers): a plan answer is ratio-like when `plan.formula.kind` is ratio / share / pp / derived / member_diff, a simple `avg`, a comparison other than `none` (growth rate), or any metric in `plan.metric_ids` is ratio / derived / avg / platform_ratio / has `percent_scale` / additivity ratio|none; a SQL answer is ratio-like when its text (strings and comments stripped) contains `/` or AVG / MEAN / AVERAGE / MEDIAN / QUANTILE / PERCENT_RANK / CUME_DIST. If the question asks a rate, the answer carries a number and the kind is NOT ratio-like (a result where the kind cannot be told, e.g. no plan and no SQL, is left alone), the result is replaced by `{status: needs_clarification, code: no_such_metric}` -> public `needs_confirm`, `confirm.kind: "no_such_metric"`, `options: []`, `facts: []`, no plan / sql / rows, route and call counts kept (so `local`, `reuse`, `plan`, `sql` are all reported as before). The text names the asked word, says no number is given because only totals / counts exist, and suggests `分子 ÷ 分母` only when the numerator is found by name in the question stem and a sales/amount metric of the same unit exists (no digits, nothing guessed). Nothing is written to the reuse cache by the guard, so the original cached answer is untouched and the guard fires on every repeat. Known cost: "平均每月销售额"-style questions answered with a plain sum by the plan lane are also stopped (conservative). `engine.confirm(requestId, ...)` on such a request returns `refused` / `refusal.code: "no_such_metric"` instead of throwing.
2. **Column types in auto mode** (`src/duck.js` `metaTypeAuto`): DATE / TIMESTAMP* / DATETIME -> `date`; integer / decimal / double / float / real -> `number`; VARCHAR with a date-like name (`date|month|日期|时间|月份|年月|日$`) -> `date`; everything else `text`. The rc.6 heuristic (`INT|REAL|NUM|DEC|DOUBLE|FLOAT...` for numbers, `date|month` in the name for dates) stays for pack mode. The core already created the time bucket dimension from the raw DuckDB type; what was missing was the registry's meta type, which is what binds it.
3. **Currency in auto mode** (`src/auto-currency.js`, run after `buildAutoPack`). The core only reads English currency column names (currency / ccy / cur). For 币种 / 货币 / 币别 / 货币代码 / ... the distinct values are read locally (ISO codes, symbols, 人民币 / 美元 / 英镑 / 欧元 / 日元 ...; only the SET of codes is kept) and the same fields the core writes for an English column are set: `_meta.currency[table] = {code | multi, codes, col, source}` (-> the SQL-lane prompt lines "含多种币种 ... 不能直接相加", which the core triggers from `_meta.currency`) and, on money metrics of that table (unit 元, or no unit and a money-like name; never 件 / 个 / counts / rates), `multi_currency: true` + empty unit (several codes) or `unit` = 美元 / 英镑 / 欧元 / 日元 / 元 / code + `currency` (one code). `currencyNoteText` in the core then appends "含多种币种，未换汇，不能直接相加" to plan-lane answers. Not covered by the core: the SQL lane's own SQL. For that, `currencyGuard` in `run()` appends the same note when the SQL reads a multi-currency money column of a multi-currency table and neither groups by nor mentions the currency column (a split by currency needs no note). `rules.preview()` adds `currencyNote`, `currencies` and `byCurrency` (per-currency totals computed locally) so the settings page does not show a mixed total as one number. The core's dictionary already maps 销售额 / 金额 / 成交额 / 营业额 / 退款额 to money metrics, so no extra alias list was needed; names it does not know (订单金额) become sum metrics with no unit, which the pass above also treats as money when the name looks like money. Currencies are never converted.
4. **Dimensions**. `engine.rules.dimensions()` mirrors `metrics()` (`id` `d:...`, `name`, `kind` column|timeBucket, `dataset`, `field`, `grain`, `formula`, `status`, `recordId`, `auto`; rejected ones are listed as `rejected`). confirm / reject / revert already worked on dimension ids internally (`autoItemOf`); what was missing was listing and preview, and `revert('d:x')` now matches records by kind when the id carries a prefix (a metric and a dimension may share a bare id). `rules.preview(id)` dispatches: `d:` ids and dimension-only records -> dimension preview `{kind:'dimension', distinct, rows, nullCount, top:[{value,count}] (5), local:true}` (time buckets are counted per bucket, e.g. month); otherwise the metric preview as before. The values are real data: computed locally, never part of a model request (nothing in the request builders reads them), and over HTTP the dimension preview is **owner-only** (metric previews stay open to askers). MCP `list_rules` lists dimensions without values, and the settings UI loads dimension previews only for the owner. CLI `rules list` prints both with `metric/<kind>` and `dimension/<kind>`; export/import carry dimensions.
5. **Confirm on a SQL-lane answer**. Cause: the core lists auto fields of a SQL answer as plain `table.column` in `tier_why.auto_names`, and `confirmAutoNames` only read the `x=y` (join) form, so nothing was flipped and the re-ask came back identical. Fix (auto mode): plain `table.column` entries are now read (SQL lane only), so an answer pending only because of auto-named fields becomes `verified`. If it is pending because of a new calculation (`tier_why.new_algos`, unregistered fields, bad joins) a click cannot change that: `confirm()` returns `refused`, `refusal.code: "sql_not_confirmable"`, text "这类新算法 1.0 还不能一键确认，请在口径里把它定义成指标。" (English text when `language: 'en'`), `route: "sql"`, and the pending request is kept; the same happens after a re-ask that is still pending (never loops). In pack mode a pending SQL-lane answer is always the new-algorithm kind, so it gets the same refusal instead of a silent repeat (confirm() only; asks are untouched). README limitation added.
6. **Friction**. CLI only: `process.emitWarning` is wrapped to drop exactly `ExperimentalWarning` whose message mentions SQLite; everything else passes (a test asserts the narrowness). `serve --token <t>` / config `surfaces.serve.token` (16-200 chars `[A-Za-z0-9._~-]`, validated; default stays random per start; `config get` / `set` print `(set)`); `serve --print-config json` prints one JSON line `{name, endpoint, port, token, tokenStable, settingsUrl, ownerKey}` instead of the text lines. English sentences found in the zh path: the two fixed confirm-card sentences in `src/status.js` ("Field meaning or calculation is auto-derived ...", "A value in the question was matched ...") now have Chinese text when `language: 'zh'` **in auto mode only** (pack mode keeps the rc.6 string so recorded confirm cards stay identical; switching it on for pack mode is one boolean in `engine.js` `finalize`). The remaining English strings are host-facing error messages (`confirm: no pending ...`, config validation), not answers or cards. Not fixed: the doubled "为避免给错数字" in some refusal texts comes from the core (`ask.js` lines 1998 / 2021 append it to a base text that already has it), and the core is frozen.
7. **UI**. `cjkSpace` inserts a space between Latin / digits and CJK in generated wording (the `_how` sentence "orders 表的 amount 列求和", the notes list); data labels and the engine's answer lines are not touched. ## rc.8 changes (src/, bin/, ui/, docs/, tests only; core/ untouched, CORE-MANIFEST.json unchanged)

Parity rule: all new work is on the data-setup / import side. `importFiles` and the engine get optional hooks (`data.plan`, `data.warehouse`, `data.maxRows`) that are absent for every pre-rc.8 configuration, so the request path, the model request bodies and the answers with a supplied pack are the rc.7 ones (the full suite, including the byte-parity test, passes unchanged; the 168-question replay is the maintainer's check).

1. **Product decision**: DuckDB is the engine's own built-in database (`@duckdb/node-api` is a dependency; nothing to install). Everything else is copied INTO it. The model's SQL runs only on the local DuckDB with external access off, exactly as before; the SQLite file / PostgreSQL / MySQL are never queried by a question.
2. **Discovery** (`src/discover.js`): only the paths given; never the disk root, never default locations. Skips hidden folders (below the named root), `node_modules`, `.git`, venvs, credential folders (`.ssh`, `.gnupg`, `.aws`, Keychains, ... refused even when named), system roots, symlinks (files and folders). Magic header first: SQLite 16 bytes `SQLite format 3\0`, DuckDB `DUCK` at offset 8, so a database with any extension (also `.csv`) is found. xlsx: sheets and used range read from the zip (`jszip`, already a dependency of exceljs) without loading cells. Database files are opened read-only (`node:sqlite` readOnly + `query_only`; DuckDB `READ_ONLY` with external access off). Files over `previewMaxBytes` (512 MB) are listed without table detail. A DuckDB file in use by another process is listed with `error:"file_in_use"`.
3. **Config**: new source types `sqlite {path, tables?, name}`, `postgres|mysql {id, name, host, port, database, user, schema?(pg), tables, ssl?}`. `name` is the table prefix (`<name>__<table>`, derived from the file / database name, de-duplicated). `data.refreshMinutes` (default 15), `data.maxRowsPerTable` (default 5,000,000), `data.warehouse` (own DuckDB location; default stays `<workspace>/warehouse.duckdb`; an existing file there is refused, never overwritten). A DuckDB-file source still excludes everything else. `password` is rejected in `estratto.json`: it is split off by `takePasswords` (init / addSource / HTTP) into `secrets.json` `connections.<id>.password` (0600). `setApiKey` keeps the connections. The workspace redactor knows every password (outputs, events, HTTP, CLI).
4. **SQLite import** (`src/snapshot.js`): one pass per table (`typeof` counts) decides the type of each column: only integers -> BIGINT, integers+reals -> DOUBLE, text -> VARCHAR, text mixed with numbers -> VARCHAR (CAST), BLOB present -> column skipped with an `import_warning` (`reason: blob_column`), empty column -> declared affinity. Dates stored as text stay VARCHAR (rc.7 auto typing handles date-like names). Refresh detection is the file's size/mtime plus a signature of the table selection (so choosing other tables re-imports that source, also after a restart: the signature is in `import.json` stamps).
5. **PostgreSQL / MySQL**: pure-JS drivers `pg`, `mysql2` (dependencies). Read-only: pg `SET SESSION CHARACTERISTICS AS TRANSACTION READ ONLY` + `default_transaction_read_only=on` and the copy runs in `BEGIN TRANSACTION READ ONLY ISOLATION LEVEL REPEATABLE READ` (one consistent snapshot of all chosen tables); mysql `SET SESSION TRANSACTION READ ONLY` + `START TRANSACTION WITH CONSISTENT SNAPSHOT, READ ONLY`. Streaming: pg `DECLARE ... CURSOR` + `FETCH 5000` (no extra package), mysql2 `.stream()`; rows go through an all-VARCHAR stage table and are CAST into the final types in batches. Types: ints -> SMALLINT/INTEGER/BIGINT (mysql unsigned widened), numeric(p<=38,s)/decimal -> DECIMAL(p,s) (otherwise DOUBLE), float -> DOUBLE, bool -> BOOLEAN, date -> DATE, timestamp -> TIMESTAMP, timestamptz -> TIMESTAMP in UTC (sessions use UTC), time / json / uuid / arrays / enums / text -> VARCHAR, bytea / blob / binary / geometry -> skipped with a warning. MySQL zero dates become NULL (the only silent conversion). The row cap is a hard refusal (`row_cap_exceeded`, message names table, count and limit; checked before copying and again while streaming); nothing is truncated. Views are listed and importable. Driver errors are scrubbed of the password before they leave the importer.
6. **Refresh**: a database source is represented to the engine by a marker file `<workspace>/sources/<id>.source`; its mtime is "when the snapshot was last asked for". The engine's existing file-change logic then re-imports only that source's tables, in one transaction (a failed refresh keeps the old tables, emits `data_refresh_failed`, and `refreshData()` now also returns `failed:[{file,message,code}]`). Manual refresh (`estratto add --refresh`, `POST /api/data/refresh`, `ws.refreshData()`) touches every marker. Auto refresh touches a marker only when `data.refreshMinutes` have passed, and only from the engine's pre-ask check, so opening a workspace (status, doctor, rules) and questions inside the interval never connect to the database. Known cost: the first question after the interval waits for the re-import; use `data.refresh: manual` for very large sources. Adding or changing a source that cannot be imported makes `saveConfig` throw and roll back (`import_failed`, `row_cap_exceeded`).
7. **Engine hooks** (src/engine.js, 6 small edits): `data.plan(file)`, `data.warehouse`, `data.maxRows` passed to `importFiles`; `statKey` / initial stamps include the plan signature; `doRefresh` collects failures; `engine.dataSummary()` (rows, columns, date range per table; the date column is the first DATE/TIMESTAMP column, preferring order-like names, or a text column with a date-like name that parses >= 90%).
8. **CLI**: interactive `init` = name -> "do you already use a SQL database?" (none / SQLite / PostgreSQL / MySQL / DuckDB) -> (none: location of the own DuckDB, default `<home>/<name>/warehouse.duckdb`) -> "where is your data?" -> numbered list (kind, name, size, rows/tables, folder) -> pick (all / 1,3 / 1-3; tables of a database file; DuckDB file only alone) -> for PostgreSQL/MySQL host, port, database, user, hidden password, schema, SSL, connection test, table list with row counts -> import with progress lines -> table / rows / date range -> model provider and hidden key -> per-metric confirmation -> MCP / serve snippets. Prompts are Chinese (`--language en` for English). The workspace is created before the model questions (the import needs it); if the import fails the new workspace is removed. Non-interactive: `--db`, `--warehouse`, `--scan`, `--pick`, `--tables`, `--pg-url`, `--mysql-url`; the database password comes from `ESTRATTO_DB_PASSWORD`; a password inside a URL is never saved in `estratto.json` (it is only a fallback when the variable is unset, with a warning, and then lives in `secrets.json`). Non-interactive output keeps the rc.7 English lines. `add` gained `--scan`, `--sqlite`, `--postgres`, `--mysql`, `--refresh`; `doctor` checks database sources (`--online` connects read-only).
9. **HTTP / UI**: `POST /api/data/discover`, `/api/data/test-connection`, `/api/data/add` for every source kind, `GET /api/data/progress` (owner only; the add request itself blocks until the import ends, the page polls progress). Settings > Data has the "add data" flow mirroring the CLI. Not done: choosing individual xlsx sheets (a workbook is imported whole), importing a DuckDB file's tables into the own warehouse (a DuckDB file is still used in place and cannot be mixed).
10. **Tests**: real PostgreSQL 16 and MariaDB 10.11 servers are started on loopback in temp dirs (`test/helpers-db.js`); tests skip with a message if the binaries are missing. They check the read-only session (INSERT refused), types, row cap, wrong password, refresh timing, and that the password appears in `secrets.json` only (all workspace files, CLI output, HTTP responses, events).
